Спроектируй архитектуру **NovaX v0.2.0** — полноценный жизненный цикл capabilities и асинхронные нотификации (фундамент перед VFS и сетью), опираясь на следующую модель без раздувания ядра:

1. **Дерево происхождения (`CDT`), `mint` и транзитивный `revoke` (`kernel/heart/src/ipc.rs`):**
   - Реализуй компактное двусвязное дерево деривации (CDT) на фиксированном статическом пуле индексов (без динамических аллокаций в куче ядра).
   - `SYS_CAP_MINT`: создаёт дочернюю копию capability в свободном слоте с урезанием прав (`old_rights & new_rights`, расширение прав запрещено) и привязывает её в CDT как потомка исходного слота.
   - `SYS_CAP_REVOKE`: транзитивно отзывает все дочерние копии указанного capability по CDT (не трогая сам корневой слот владельца), очищает отозванные слоты и **обязательно размаппливает (`unmap` + TLB flush)** соответствующие виртуальные страницы из `PML4` процессов-владельцев, если это `Mmio` или `Dma` / разделяемый буфер.

2. **Передача capabilities по IPC и `reply-cap`:**
   - Расширь заголовок IPC-сообщения поддержкой передачи **ровно одного `cap_slot`** (с опциональным урезанием прав при передаче и записью в CDT).
   - В `SYS_CALL` (синхронный запрос-ответ) ядро генерирует для сервера одноразовый **`reply-cap`**, который автоматически сгорает после первого `SYS_REPLY` (не позволяя серверу спамить клиенту позже и не раскрывая глобальный ID потока).

3. **Асинхронные нотификации (`CapKind::Notification`):**
   - Добавь легковесный объект ядра `Notification` (атомарное 64-битное слово `AtomicU64` битовой маски событий + очередь ожидания).
   - Сисколлы:
     - `SYS_NOTIFY_SIGNAL(cap, badge)` — атомарный `fetch_or(badge)` в слово нотификации и пробуждение ждущего потока.
     - `SYS_NOTIFY_WAIT(cap)` — если маска `!= 0`, атомарно забирает и обнуляет её (`swap(0)`), иначе переводит поток в ожидание.
     - `SYS_NOTIFY_POLL(cap)` — неблокирующий `swap(0)` для интеграции с event loop / `Future::poll()` (`async/await`) в Ring 3.
   - Добавь возможность привязки аппаратного IRQ и события завершения/падения дочернего процесса (`fault` / `exit`) к `Notification` с заданным `badge`.

4. **Эталонный интеграционный тест супервизора (`tools/v02_test.sh`):**
   - Реализуй сквозной сценарий проверки без костылей под конкретный тип драйвера:
     1. Супервизор (`init`) создаёт тестовый сервер/драйвер, минтит ему урезанный capability на ресурс (`Endpoint` / буфер) и привязывает его выход/падение к своему `Notification`.
     2. Клиент минтит read-only capability на свой буфер памяти, отправляет его серверу через IPC и получает ответ по одноразовому `reply-cap`.
     3. Сервер имитирует аварийное падение (`crash` / fault).
     4. Супервизор пробуждается по `Notification`, вызывает `SYS_CAP_REVOKE` на корневом capability (ресурсы и маппинги упавшего сервера отзываются), после чего спавнит replacement-экземпляр сервера, и клиент успешно завершает повторный запрос без перезагрузки ядра.
   - Все существующие регрессии (`./tools/test.sh` и `./tools/m6_test.sh` .. `./tools/m9_test.sh`) и `cargo clippy --workspace --all-targets -- -D warnings` должны оставаться зелёными.
